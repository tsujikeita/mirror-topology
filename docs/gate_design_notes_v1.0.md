# Reproducibility gate design notes v1.0
2026-08-31。テーマTの遡及監査（Step 0・T1・T2a・T2b-2）で実際に発生した事故と，それを受けて
設計したhard gateの記録。**次の解析（Step 1）で同じ枠組みを再利用するための設計書**であり，
論文の再現性セクションの素材でもある。

原則は一つ：**「正しい結果が出ているように見えること」を信用せず，「その結果が本当にその
コードから出たこと」を機械的に証明する。**

---

## 1. ソース同一性（G01系・G02）

### 1.1 untracked false-pass
初期のgit gateは「作業ツリーが清潔か」を`git status`で見ていたが，**未追跡（untracked）の
ファイルは清潔判定に含まれない**ため，コミットされていないコードで実行しても通過してしまった。
→ **HEADのblobと実行中ファイルを直接比較**する方式へ変更（`git show HEAD:<path>`）。
さらに`gate_selftest`（意図的にuntrackedを作ってFAILすることを常設確認）を追加。

### 1.2 出力の書き戻し
Colabは実行結果をノートブック自身へ自動保存するため，実行中にノートブックが「変更あり」に
なる。素朴な清潔判定はここで必ず落ちる。
→ 清潔判定から**実行中ノートブック自身のみ**を除外し，代わりに**source-only SHA**
（コードセルの内容だけのハッシュ）で同一性を判定。

### 1.3 エディタの空白正規化
Colabは保存時に行末空白を削る。解析内容が1バイトも変わっていないのにハッシュがずれ，
ゲートが偽陰性で停止した（実機で発生：セル10の行末空白1個）。
→ **canonical form**（CR除去・行末空白除去・末尾空行除去）でハッシュを計算。
内容の変更は従来どおり検出される（H0を1箇所変えれば即FAILすることを確認済み）。

### 1.4 転送経路の終端改行
アップロード経路が`.py`の末尾に改行を1個付加し，HEADと実行中ファイルのバイト比較が落ちた。
→ コードファイルの照合も**canonical text比較**に統一。生バイト一致は`matches_raw`として
provenanceに併記（監査可能性は失わない）。

### 1.5 live notebook identity
ディスク上のファイルが正しくても，ブラウザで開いている実行中のノートブックが未保存編集を
含む可能性がある。
→ Colabの`get_ipynb`で**実行中ノートブック本体のsource-only SHA**を取得し，HEADと照合
（`nb_live_match`）。T2b-2本番で初発動し，以後すべてのofficial実行で必須条件。

### 1.6 public commit の事前性
「結果を見る前に公開commitしていた」ことを保証するため，**canonical origin URL照合**と
**push済み検証**（`ls-remote`）をOFFICIAL必須条件に編入。

## 2. 依存の凍結（G06系）

### 2.1 commit pinning
外部リポジトリ（CMBtopology）をHEADで使うと，将来の更新で結果が変わる。
→ **commit hashで固定**し，`rev-parse HEAD`で照合。

### 2.2 hermetic clone
Drive上に置いた作業コピーは同期や過去セッションの影響で改変され得る（実機で全trackedファイルが
modified扱いになりofficial実行が停止）。
→ 依存ソースは**セッション毎にephemeral領域へ新規clone**。既存があれば`checkout --force`＋
`clean -fdx`で復元し，復元の有無を`ct_repair`として記録。それでも不一致ならFAIL。

### 2.3 tracked clean と canonical origin
commitが正しくてもソースが手元で改変されている事故を防ぐため，
`git status --porcelain --untracked-files=no`が空であること，originが正準URLであることを
それぞれhard gate化。

### 2.4 依存内部の設定まで照合
CMBtopologyが内部で使うCAMB設定（H0・ω_b・ω_c・m_ν・τ・A_s・n_s・lensed/unlensed・単位）を
**ソースから機械抽出**し，凍結期待値と一致することを確認（G06d）。これを怠ると，等方極限の
絶対振幅gateが「宇宙論パラメータの差」と「有限体積効果」を混同する（実測で5%の差があった）。

## 3. 入力データの検証（G09・G11・G18・G19）

### 3.1 生成物のbinding
`runs/`から最新更新時刻のディレクトリを拾う方式は，並行実行や再利用で取り違えを起こす。
→ 生成**前後のディレクトリ集合の差**で新規1個を特定し，パラメータトークンで再検査。
再利用時は**毎回file SHAをmanifest記録値と照合**。

### 3.2 対称性の許容値を流用しない
解析的に構成した共分散向けの厳密許容値（1e-10）を，数値積分で作られた共分散に流用したため，
初回の実データ接触で停止した（reality違反5.01e-08＝パイプラインとして正常な水準）。
→ **閾値を緩めるのではなく**，理論上厳密な対称性（Hermiticity・reality条件）を満たす
部分空間へ**明示的に直交射影**。除去量を全点で記録し，生違反に較正上限（1e-5），補正量に
凍結上限（1e-6），射影後に機械精度を要求。**較正上限は「実データ接触後・科学出力を見る前に
凍結した」ことを明記する**（事前登録値ではない）。

### 3.3 射影の安全性は代数で示す
「射影してもE[S±]がほとんど変わらない」は安全性の根拠にならない。E[Q]=tr(P·C)でPが実対称
なら反対称成分は**恒等的に**落ちるからである。
→ 恒等式 `C_real_projected = (C_real_raw + C_real_rawᵀ)/2` を直接hard assertし
（G09d），これ1本で**全軸・全射影について**平均保存を保証。E[S±]比較は
「実装整合性チェック」に降格。

### 3.4 PSDの扱い
Cholesky＋jitterは負固有値を隠す。
→ **固有値分解**に変更し，有意な負固有値はFAIL・丸め水準のみclip・
λ_min/clip量/有効ランクを全点で記録。

## 4. 完了性と偽PASS（G20・G21・G25）

### 4.1 期待集合との完全一致
「エラーなく走った」は完了の証明ではない。旧コードには，行列が見つからない点を黙って
skipしたまま全点成功と表示する経路があった。
→ **期待キー集合と実測集合の集合等価**をassert（missing・unexpected・duplicatesを個別報告）。

### 4.2 構造的NaNを誤検出しない
wide形式の出力では，topologyごとに存在する演算子列が異なるため**構造的NaN**が必ず生じる。
素朴な`notna().all()`は正常な完走を誤FAILさせる（実際にofficial実行直前に発見）。
→ **行ごとに「適用可能な列のみ」**をfinite検査。

### 4.3 新しい成果物にもfinite gateを掛ける
派生CSV（比率列など）に`inf`/`NaN`が入っても，主CSVだけを見るgateは通ってしまう。
→ 成果物ごとにfinite gateを用意し，ゼロ除算の定義域checkも入れる。

## 5. 解析設計上の教訓

### 5.1 選択効果を統計と混同しない
大域走査で`argmin S⁺`を選ぶと，S⁺+S⁻が軸に依らないため**S⁻は構造的に増大する**
（等方nullで中央値1.77倍）。この値を観測のS⁻と直接比べてはならない。
→ 観測側にも**同一の走査規則**を適用したjoint分布で比較する（Step 1の設計要件）。

### 5.2 座標軸は誤りを隠す
実装誤り（軸の画素中心への丸め・実空間共分散の共役方向）は，座標軸上では偶然一致して
露呈しないことがある。実際に一般軸で67%の誤差が出た実装が，ŷ軸では正しく見えた。
→ **一般軸を含む自己検証**を必ず入れる。

### 5.3 誤差源は逐次分解として記述する
複数の実装選択が重なった誤差を分解するときは，**凍結した診断経路に沿った逐次差分**として
記述する（B−A・C−B・D−C・E−D）。数学的に直交・一意な分解ではない。

### 5.4 比率の向きを明示する
旧実装の`A_over_dE = A/dE`と新実装の`estimate_over_A = dE/A`は逆数であり，取り違えると
「再現した」と誤認する（実際に起きた）。
→ 成果物には**両方の向き**を保存し，どの列が歴史的量と比較可能かを機械的に明示する。

### 5.5 表現をデータより強くしない
「S⁺抑制は存在しない」「全域で系統的」といった表現は，実際には
「検査した範囲で・被覆言明として」しか言えないことが多い。
→ **coverage statement**として書く。0/N は確率言明ではない。

## 6. 運用プロトコル

1. 旧コード → 外部レビューによる独立監査
2. 修正版の作成（**新規エンジンを増やさず，凍結済みコードを継承する**）
3. **実行前**の再監査（この段階でthresholdを凍結し，以後緩めない）
4. commit & push（＝結果を見る前の凍結点）
5. smoke（少数点・全経路を通す対象を明示選択）→ 成果物を独立検算
6. official（純正ノートブックをRuntime restart→Run all）→ 成果物を独立検算
7. freeze（タグ・凍結記録・canonical exportの照合）

**版を上げるたびに再監査するのではなく，「科学計算に触れない修正」と「触れる修正」を
区別する**ことで往復回数を抑えられる（実例：rules同期のみの版では再smokeを省略）。
