## 0. 到達点と主張の範囲
- **family partial**（`calibrate_family_partial`）：1 family の全 surviving size・両 system・正式 plan・required 入力に対し，既存 `run_first_wave(_stage='calibrate_sealed')` と**同じ per-pseudo 手続き**（parent 組立 → gate 前 fingerprint → gate → 共通 threshold evaluator → parent／plan／position source／12 位置完全 Result の content-addressed 保存 → gate 後 fingerprint）を 1 family に限って実行し，`family_partial_calibration_v1` record（archive identity kind `family_partial_calibration`）を発行する。**partial は c／u／n・Wilson・usable・label を発行しない**（`calibration` key を持たない；`load_sealed_record` は identity kind で拒否）。

## 2. 既存 module の変更（3 件；いずれも数値計算の変更ではない。受入れ判断をお願いする）
### 2.1 `threshold_evaluator._w2_position_map`（R-D4C1-W2POS）
small-bank self-test で判明：**登録 D-2W context の W₂ manifest は position を configuration id（例 E7/L1.00＝30101／30102／30103）で識別**する（`w2_cases`／`intake_w2_position_bank` の `position_id=cid`）一方，runner の case position map と `_case_positions`／run reader は観測位置 1..3 を要求し，`orchestrator._w2_context_for_inputs` は map の値集合＝manifest の position 集合を要求する。従って 0.105.0 のままでは**登録 context は evaluator から一切消費できない**（`one-case position map must cover all three evaluated configurations and the W2 manifest positions` で停止；B-2 期の合成 context は position 1..3 だったため顕在化しなかった）。対応：`evaluate_family_full` の診断（`evaluate_threshold`）に渡す map だけを，view の grid identity（evaluation id → 登録 configuration id）で manifest の id 空間へ翻訳し，**登録 id 規則（configuration suffix＝観測位置）**と 3 id の完全一致を要求する（grid identity なし・対応しない manifest は拒否）。case position record／position_probabilities／transition／reader の 1..3 は不変。`orchestrator.py` は不変。試験：合成（identity）・登録 context（翻訳）・suffix 不一致・id 集合不一致・grid identity なしの拒否；partial E2 の small-bank self-test は登録 context（9 case・context SHA＝pins）で通過。
### 2.2 `checkpoint._verify_Q_side` の `MIXTURE_TOL`（R-D4C1-MIXTOL）
合成 4 family の W₂-only trigger variant で，36 配置 native 12 位置 mixture の bootstrap replicate `num` に **1.0000000000000002**（`P @ w`；各 P は hits/N で正確に ≤1，w は 1/36×36）が現れ，reader の厳密な `num <= 1` が正しい record を `stored seed 4 num/den out of the probability domain` で拒否した。この reader は `verify_run_references` → Phase E の `evaluate_sealed_target` も通るため，**単一 process の seal でも同じ条件で Phase E が止まる**潜在不具合。対応：mixture（`per_seed` の num／den）の定義域検査に `MIXTURE_TOL = 8·eps`（≈1.8e-15）の丸め余裕；per-configuration の P（`0 <= P <= 1`）は厳密のまま；余裕を超える値・負値は従来どおり拒否。CI の再現・Q・精度・判定の検査は不変。試験：当該 record（値 1+1ulp）の受入れと 1+1e-12／負値／per-config 1+1ulp の拒否。
### 2.3 `archive.Archive`（R-D4C1-ARCHIVE；F.4 の実測）
0.105.0 の archive は put ごとに index.json 全体を再 parse・再書込み（put 時間 ∝ entries），get ごとに全 parse。実測（sandbox，別 process の試験と並走）：1000 put 31.9 s・index 1000 entry で 200 get 2.7 s（13.6 ms/get）。正式 1 family≈12,000 put（2000 pseudo × parent＋plan＋3 position source＋12 位置 Result）では index 書換えだけで≈1.3 h／family，merged 48k entry の reader（≈40k get）は≈7 h と見積もられ，D4C-2 の実行と reader を不能にする。対応（on-disk 形式・index bytes は不変；試験で immediate／deferred の index.json bytes 一致を確認）：(i) parse 済み index を stat identity（inode・size・mtime_ns・ctime_ns）で無効化する in-memory cache と (kind, sha) map（get O(1)）；(ii) `deferred_index=True`（record file は即時書込み・fsync，index は `flush()`／context exit／`flush_every` で書込み；pending 中の外部変更は conflict）；(iii) `import_bytes`／`merge_archives`（別 process の partial archive を bytes 同一で統合；SHA・canonical bytes・identity conflict・source engine 版を検査）。実測：deferred 1000 put 4.1 s（record file の fsync が支配）・200 get 0.04 s。外部編集の検出（stat 変化）と pending 中 conflict は試験済み；敵対的な同時書換えには元々非対応（docstring のとおり）。
